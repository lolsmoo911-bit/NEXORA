## 1. The point of this phase

A specification enforced by one codebase asserting its own correctness is not a
specification. So AID has **two independent implementations**:

| Implementation | Language | Result |
|---|---|---|
| `aid/src/aid.mjs` | JavaScript | `# tests 40 / # pass 40 / # fail 0` (later runs: 40) |
| `aid/src/Aid.sol` | Solidity, Foundry | `Ran 16 tests … 16 passed; 0 failed` |

Both assert the **same seven vectors**, generated by `aid/test/emit-vectors.mjs` and
committed to `aid/vectors.json`. The Solidity suite was written against the specification text
and pinned to the JavaScript output; it is a genuine cross-check, not a restatement.

## 2. The scheme

```
assetId          = keccak256(0xA1 || domainSeparator || assetType || assetKey)
domainSeparator  = keccak256(abi.encode(chainId, specVersion))
```

Fixed-width encoding throughout. That is the entire safety argument: a variable-length
concatenation lets two different assets produce the same preimage bytes, so the widths are a
correctness requirement, not a style choice.

Domain separator for NEXORA (chain 902024, spec v1):

```
269e6cd679db004a2c778774b6c0a8598ce1024d2db17a3ef9456d0b41097c8f
```

## 4. Tests that attack rather than decorate

- **Fuzz for collisions.** 20,000 iterations across five chain ids, asserting that no two
  *distinct* tuples share an `assetId`. It compares distinct tuples only, because two
  identical tuples producing the same id is determinism, not a collision — an earlier version
  of this test got that wrong and reported a collision on `native:1 == native:1`.
- **Property.** Changing any single field — tokenId, address, type, chainId — changes the
  `assetId`.
- **Rejection.** Unknown asset types, unknown spec versions, malformed addresses, non-32-byte
  keys, out-of-range uint256, and non-canonical text are all rejected rather than coerced.
- **Boundary strictness.** `fromCanonicalString` **rejects** uppercase instead of lowercasing
  it. Accepting two spellings of one identifier defeats the purpose of a canonical form, and
  the first implementation normalised when it should have refused.

## 5. The failure worth recording

The first keccak-256 in this repository was **hand-written**. It was wrong: the pi lane
destination was transposed. The failure was **invisible to every test except the known-answer
vectors**, because a hash that is deterministic and returns 32 bytes is exactly what the AID
library expects from it — stable, plausible, meaningless.

What changed, and stays:

1. `aid/src/keccak.mjs` delegates to a pinned dependency. A cryptographic permutation is not
   something to improvise.
2. `aid/test/keccak.test.mjs` keeps the KAT vectors permanently, including one asserting the
   result is **not** SHA3-256 — the two differ only in a padding byte, so a plausible wrong
   answer is otherwise undetectable.
3. The incident is written into `aid/SPEC.md` §11 rather than left in history.

## 6. Supply-chain change made along the way

`foundry-rs/foundry-toolchain@v1` with `version: stable` was replaced by a pinned `v1.8.5`
tarball verified against the release's published digest. Two measured reasons: the action
resolves the newest release at run time, so two runs of the same commit can test against
different compilers; and it fetches a signature attestation from an endpoint that returned
HTTP 504 on two consecutive runs, taking the whole job down.

## 7. Limits

`assetId` is an identifier, **not an attestation**: anyone can compute the id of an asset that
does not exist. Existence, ownership and metadata are a registry concern, and the registry
(P5) stores a *claim*, not proof. Collision resistance is inherited from keccak-256 and has
not been independently reviewed. **Nothing in this phase has been audited.**
