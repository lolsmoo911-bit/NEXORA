# خطة تطويرية بدون تكلفة (أكثر من 15 مرحلة)
## تطوير جزء البلوكشين والسيرفرات للاقتراب من رؤية NEXORA

> **القيود:** بدون تكلفة، بدون بنية تحتية مدفوعة، بدون نشر عام، بدون بيانات سوق مدفوعة، وبدون معاملات حقيقية على شبكات عامة.  
> **الهدف:** الاقتراب تقنيًا من الرؤية (منصة تداول/مضاربة وامتلاك تدريجي لأصول رقمية مرتبطة بأصول حقيقية) عبر **تصميم وتنفيذ محلي/محاكاة** قابل للتحقق.  
> **الحالة:** مسودة تنفيذية (تُحدّث مع التقدم).

---

## المرحلة 1 — تثبيت الرؤية التقنية والنطاق (Vision & Scope Baseline)
- **الهدف:** تحويل الرؤية إلى متطلبات تقنية واضحة وقابلة للتنفيذ محليًا.
- **المهام:**
  - تعريف أنواع الأصول المستهدفة (عملات، معادن، طاقة، أسهم، سندات، صناديق) ونماذج تمثيلها.
  - تحديد حالات الاستخدام الأساسية: إصدار/تمثيل، تداول/مضاربة (محاكاة)، محفظة، تسعير، تقارير.
  - توثيق "ما هو محاكى محليًا" مقابل "ما يحتاج موارد خارجية لاحقًا".
- **المخرجات:** وثيقة نطاق تقنية + مصفوفة متطلبات.
- **معيار القبول:** وثيقة واحدة مرجعية متفق عليها داخل المستودع.

## المرحلة 2 — معمارية النظام (Blockchain + Server Architecture)
- **الهدف:** تصميم معماري واضح يفصل الطبقات والمسؤوليات.
- **المهام:**
  - تحديد الطبقات: Chain Contracts، Indexer/State Reader، Market/Pricing، Matching/Trading Engine، API، Storage (محلي).
  - تعريف واجهات بين الطبقات (inputs/outputs/events).
  - رسم تدفقات: إصدار أصل، تسجيل سعر، إنشاء أمر، مطابقة، تسوية محاكاة.
- **المخرجات:** مخططات معمارية + عقود واجهات (interfaces/specs).
- **معيار القبول:** كل تدفق أساسي موثق بمدخلات/مخرجات وأحداث.

## المرحلة 3 — توحيد نموذج الأصول والهوية (Asset Model & AID Alignment)
- **الهدف:** جعل تمثيل الأصول متسقًا عبر السلسلة والسيرفر.
- **المهام:**
  - توسيع/توحيد نموذج الأصل (asset type, metadata schema, lifecycle states).
  - مواءمة `AID` و`AssetRegistry` مع تصنيفات الأصول المستهدفة.
  - تعريف قواعد التسمية والتحقق (official/custom, provenance metadata).
- **المخرجات:** مخطط بيانات موحد + تحديثات عقود/اختبارات عند الحاجة.
- **معيار القبول:** نفس الأصل يُعرّف ويُتحقق منه بنفس القواعد في العقود وطبقة السيرفر.

## المرحلة 4 — عقود تمثيل الأصول (Tokenization Primitives, Local/Test)
- **الهدف:** بناء بدائل عقود لتمثيل الأصول (محليًا/اختباريًا).
- **المهام:**
  - تصميم عقود تمثيل (fungible/non-fungible/semi-fungible حسب الأصل) كطبقة اختبارية.
  - دعم mint/burn/transfer مع ضوابط أدوار (roles) وحالات (paused/active).
  - ربط التمثيل بسجلات الهوية (AID/AssetRegistry) حيث مناسب.
- **المخرجات:** عقود + اختبارات Foundry.
- **معيار القبول:** سيناريوهات إصدار/نقل/حرق أساسية تمر محليًا.

## المرحلة 5 — نموذج التسوية والضمان (Settlement & Collateral Model - Simulated)
- **الهدف:** نمذجة التسوية والضمان بدون أصول/مدفوعات حقيقية.
- **المهام:**
  - تعريف حالات التسوية (pending, matched, settled, failed, cancelled).
  - تصميم نموذج ضمان محاكى (virtual collateral/margin) وقواعد التصفية المنطقية.
  - توثيق الفجوة بين المحاكاة والتسوية الحقيقية.
- **المخرجات:** مواصفة تسوية + عقود/منطق محاكاة + اختبارات.
- **معيار القبول:** سيناريوهات مطابقة/تسوية/فشل قابلة لإعادة الإنتاج محليًا.

## المرحلة 6 — طبقة الأوراكل المحاكاة (Mock Oracle & Price Feeds)
- **الهدف:** توفير تغذية أسعار/بيانات "شبيهة بالحياة الواقعية" محليًا بدون مزودين مدفوعين.
- **المهام:**
  - بناء Mock Oracle (on-chain interface + off-chain/local feed generator).
  - دعم أصول متعددة (FX، معادن، طاقة، أسهم/سندات كمؤشرات محاكاة).
  - إضافة حالات جودة البيانات (fresh/stale/outlier/unavailable).
- **المخرجات:** عقود/وحدات Oracle محاكاة + اختبارات.
- **معيار القبول:** المستهلكون (عقود/سيرفر) يتعاملون مع تحديثات السعر والحالات الحدّية بشكل حتمي.

## المرحلة 7 — تكامل Market Core مع التسعير التشغيلي (Pricing Service Integration)
- **الهدف:** استخدام `source/market` كأساس لخدمة تسعير/تقييم محلية.
- **المهام:**
  - تغليف وحدات التسعير (سندات، منحنيات، spreads، FX، سيناريوهات) في واجهة خدمة داخلية.
  - دعم مدخلات من Mock Oracle وملفات بيانات محلية.
  - إنتاج مخرجات تقييم موحدة (valuation, risk metrics, scenarios).
- **المخرجات:** وحدة/خدمة تسعير + اختبارات تكامل.
- **معيار القبول:** تقييمات قابلة لإعادة الإنتاج لنفس المدخلات.

## المرحلة 8 — محرك أوامر ومطابقة محلي (Matching Engine - Simulated)
- **الهدف:** بناء نواة تداول/مضاربة محاكاة على جانب السيرفر.
- **المهام:**
  - تنفيذ دفتر أوامر مبسط (limit/market/cancel) و/أو AMM محاكى (حسب التصميم).
  - منطق المطابقة (matching), الرسوم الافتراضية، وتوليد أحداث التداول.
  - منع الحالات غير الصالحة (رصيد غير كافٍ محاكى، أوامر مكررة، إلخ).
- **المخرجات:** خدمة matching engine + اختبارات وحدة/تكامل.
- **معيار القبول:** سيناريوهات تداول محاكاة (وضع/مطابقة/إلغاء) تمر بحتمية.

## المرحلة 9 — دفتر المحافظ والمراكز (Portfolio & Positions Service)
- **الهدف:** تتبع المحافظ والمراكز والأرباح/الخسائر في بيئة محاكاة.
- **المهام:**
  - نمذجة الحسابات، الأرصدة، المراكز، الأوامر المفتوحة، وسجل العمليات.
  - حساب PnL, exposure, and basic risk flags باستخدام التسعير/الأسعار المحاكاة.
  - دعم لقطات حالة (snapshots) قابلة لإعادة البناء.
- **المخرجات:** خدمة محافظ/مراكز + اختبارات.
- **معيار القبول:** تطابق الأرصدة والمراكز مع سجل الأحداث بعد إعادة التشغيل/إعادة البناء.

## المرحلة 10 — طبقة الفهرسة والأحداث (Indexer & Event Processor)
- **الهدف:** تحويل أحداث السلسلة/السيرفر إلى حالة قابلة للاستعلام.
- **المهام:**
  - بناء Indexer محلي يقرأ أحداث العقود (من devnet/local logs أو RPC محلي).
  - معالجة idempotent للأحداث وإعادة التشغيل الآمن (replay-safe).
  - تخزين محلي منظم (DB/ملفات بحسب المتاح) مع نماذج قراءة سريعة.
- **المخرجات:** Indexer + مخطط تخزين + اختبارات replay/idempotency.
- **معيار القبول:** إعادة معالجة نفس الأحداث لا تُنتج ازدواجية أو فساد حالة.

## المرحلة 11 — واجهات API للخدمات الأساسية (Core APIs)
- **الهدف:** توفير واجهات برمجية موحدة للتكامل مع واجهات المستخدم/الأدوات.
- **المهام:**
  - تصميم وتنفيذ APIs للأصول، الأسعار المحاكاة، الأوامر، الصفقات، المحافظ، والتقييم.
  - توحيد الأخطاء، التحقق من المدخلات، والتوثيق (OpenAPI/spec داخلي).
  - فصل واضح بين عمليات القراءة (query) والكتابة (commands).
- **المخرجات:** API endpoints + عقود واجهة + اختبارات.
- **معيار القبول:** سيناريوهات end-to-end محلية تعمل عبر API.

## المرحلة 12 — نموذج الهوية والصلاحيات (Identity, Roles & Permissions - Local)
- **الهدف:** ضبط الوصول والأدوار بدون بنية هوية مدفوعة.
- **المهام:**
  - تعريف أدوار محلية (admin/operator/trader/viewer/auditor).
  - تطبيق صلاحيات على APIs والعمليات الحساسة (إصدار، إيقاف، إعدادات سوق).
  - تسجيل تدقيقي (audit log) للأحداث الإدارية.
- **المخرجات:** طبقة authz/roles محلية + اختبارات.
- **معيار القبول:** كل عملية حساسة مقيّدة بدور واضح ومسجلة.

## المرحلة 13 — سير عمل إصدار الأصول (Asset Issuance Workflow)
- **الهدف:** بناء مسار متكامل لإصدار أصل رقمي تمثيلي (محاكاة) وربطه بهويته.
- **المهام:**
  - تدفق: تعريف الأصل → تسجيل/تحقق الهوية → نشر/ربط عقد التمثيل → تفعيل التداول المحاكى.
  - قوالب metadata لأنواع الأصول المختلفة (نقد، معدن، طاقة، سهم، سند، صندوق).
  - فحوصات تحقق قبل التفعيل (validation gates).
- **المخرجات:** workflow موثق + أدوات/سكربتات محلية + اختبارات.
- **معيار القبول:** إصدار أصل تجريبي جديد من البداية للنهاية محليًا.

## المرحلة 14 — إدارة دورة حياة السوق (Market Lifecycle & Controls)
- **الهدف:** التحكم في حالات السوق والأصول بشكل آمن ومنضبط.
- **المهام:**
  - حالات السوق/الأصل: draft, active, halted, suspended, retired.
  - آليات إيقاف/استئناف (circuit-breaker محاكى، pause controls).
  - قواعد انتقال الحالة والتحقق منها.
- **المخرجات:** منطق دورة حياة في العقود/السيرفر + اختبارات حالات.
- **معيار القبول:** لا يمكن الانتقال لحالة غير صالحة، وكل انتقال مسجّل.

## المرحلة 15 — المراقبة المحلية والرصد (Observability & Local Ops)
- **الهدف:** جعل النظام قابلًا للملاحظة والتشخيص محليًا.
- **المهام:**
  - سجلات منظمة (structured logs) للأحداث الحرجة (أوامر، مطابقة، تسوية، أسعار، أخطاء).
  - مؤشرات صحة (health checks) للخدمات والمحرك والـ indexer.
  - سكربتات تشغيل/إيقاف محلية وrunbooks.
- **المخرجات:** health endpoints/logging conventions/runbooks.
- **معيار القبول:** يمكن تتبع مشكلة من API إلى المحرك/العقد/الفهرس عبر السجلات.

## المرحلة 16 — الأمان والصلابة (Security Hardening & Abuse Resistance)
- **الهدف:** تقليل المخاطر المنطقية والتشغيلية في البيئة المحلية/الاختبارية.
- **المهام:**
  - مراجعة تهديدات (threat modeling) للمسارات: إصدار، تداول، تسعير، صلاحيات، فهرسة.
  - اختبارات خصومية/حدّية (fuzz/property/invariants) للعقود والمحرك.
  - تعزيز التحقق من المدخلات، حدود المعدلات المنطقية، وإدارة الأخطاء.
- **المخرجات:** تحديثات اختبارات/حمايات + تقرير مخاطر محلي.
- **معيار القبول:** عدم وجود ثغرات منطقية حرجة معروفة ضمن النطاق المحلي المختبر.

## المرحلة 17 — التكامل الشامل والمحاكاة الطرفية (End-to-End Simulation)
- **الهدف:** إثبات قابلية السيناريو الكامل للعمل محليًا.
- **المهام:**
  - سيناريو E2E: إصدار أصول متعددة → تغذية أسعار محاكاة → أوامر/مطابقة → تحديث محافظ → تقييم مخاطر.
  - إعادة التشغيل وإعادة البناء (restart/replay) والتحقق من اتساق الحالة.
  - قياس أداء محلي أساسي (latency/throughput على بيئة dev).
- **المخرجات:** سكربتات/اختبارات E2E + تقرير نتائج.
- **معيار القبول:** السيناريو الكامل يعيد نفس النتائج (حتمي/قابل لإعادة الإنتاج) ضمن نفس المدخلات.

## المرحلة 18 — التوثيق، الحزم التجريبية، وبوابة الجاهزية للمرحلة التالية
- **الهدف:** تحويل ما بُني إلى حزمة تطويرية واضحة تمهّد للانتقال (عند توفر موارد) إلى testnet عام.
- **المهام:**
  - توثيق كامل: المعمارية، العقود، APIs، نماذج البيانات، سيناريوهات التشغيل، القيود.
  - إعداد "Demo Pack" محلي (بيانات محاكاة، سكربتات تشغيل، سيناريو عرض).
  - تحديد فجوات الانتقال إلى Phase 7/8 (بنية تحتية، أوراكل حقيقي، امتثال/قانون، تدقيق).
- **المخرجات:** حزمة وثائق + سكربتات demo + قائمة فجوات جاهزية.
- **معيار القبول:** يمكن لمطور جديد تشغيل وفهم النظام محليًا ومراجعة ما تحقق وما هو محجوب خارجيًا.

## ملاحظات تنفيذ (بدون تكلفة)
- **التنفيذ الافتراضي:** محليًا فقط (devnet محلي، تخزين محلي، بيانات محاكاة/ملفات).
- **لا يتضمن:** استضافة عامة، RPC عام، مزودي بيانات مدفوعين، أوراكل إنتاجي، وصاية/امتثال قانوني فعلي، أو تدقيق خارجي.
- **مقياس التقدم:** كل مرحلة تُغلق بتوثيق + اختبارات + أدلة تشغيل محلية (قابلة لإعادة الإنتاج).
